## 3. Findings

**F1. B — After a committed accept or restore, Retry now resends the mutation and reports failure.** *Demonstrated in the browser.*

- **Code.** `apps/studio/src/routes/+page.svelte`. `perform()` (`:54`) and the connection listener (`:48`) store the *whole action* as `retryAction`. `acceptProposal` (`:258`) re-reads the Proposal, view and history after the command succeeds (`:271-281`); `restoreRevision` (`:287`) re-reads the view and history (`:302-306`). If those reads exhaust their retries, **Retry now** (`:69`) re-runs the mutation. That command succeeded, so the retry module never marked it ambiguous and does not reconcile it.
- **Reproduction.** Studio in PostgreSQL mode, real page in Chromium. Edit, Review changes, Accept. PostgreSQL is stopped as the accept response returns. The refresh reads get four 503s; the banner appears. PostgreSQL restarts; Retry now.
- **Effect.** Accept: the page shows "Proposal not accepted: Proposal is already resolved" while PostgreSQL holds the acceptance at revision 1. Restore: "Restore not applied: Document version changed from 1 to 2" while the restore is revision 2; the editor keeps the pre-restore text. `proposeChanges` (`:211`) has the same shape: a failed post-create read makes Retry now send a second `CreateProposal`.
- **Integrity.** Held. One ChangeSet each; the resend was rejected by the server's terminal and scoped preconditions.
- **Correction.** Once a command returns `ok`, never retry the command: show its result immediately and make the post-commit refresh retry only the refresh (for example `retryAction = () => openVersion(selectedVersionId)`). Add a browser test in which the command succeeds and the subsequent reads fail until exhaustion.

**F2. B — `CreateProposal` reconciliation reports an older Proposal as the one just created.** *Demonstrated over HTTP.*

- **Code.** `apps/studio/src/lib/authoring-retry.ts:140-146` accepts the first pending Proposal whose source is the same Draft.
- **Reproduction.** Draft D → Proposal P1 (text "FIRST"). D is saved again ("SECOND"). `CreateProposal(D)` loses its connection: (a) the insert never reaches PostgreSQL, or (b) it commits and the acknowledgement is lost.
- **Effect.** In both cases the client reports `proposal-created` with **P1** and its superseded text. In (a) the newer edit was never proposed. The Studio path is ordinary: Review changes, edit, Review changes again. The review panel then presents superseded content as the current proposal.
- **Integrity.** Held; no history is involved. This is a false success produced by reconciliation.
- **Correction.** Read the Draft and accept only a pending Proposal from it whose `createdAt` is not earlier than the Draft's `updatedAt`; otherwise keep the outcome unknown. Add a unit test with two Proposals from one Draft.

**F3. B — Connection loss between queries of a transaction returns non-retryable 500 `STORE_REJECTED`.** *Demonstrated.*

- **Code.** `packages/v2-core/src/postgres-authoring-store.ts`. `inTransaction` (`:108-142`) records the connection error, discards the client, then rethrows the *next query's* error (`:135`). That error is pg's `Client has encountered a connection error and is not queryable`, which `isPostgresUnavailable` (`:57-74`) does not recognize.
- **Reproduction.** (1) Termination sweep (§4): 72 of 141 kill points surfaced this error. (2) `pg_ctl restart -m fast` under 8 in-process workers: 16 of 31 connection errors. (3) Deterministic, over HTTP: acceptance blocked on a row lock; the Studio process suspended; lock released; PostgreSQL ends the idle transaction after 30 s with `25P03`; Studio resumed → **HTTP 500 `STORE_REJECTED`**, logged as `code: 'unknown'`.
- **Frequency.** In three HTTP-level restart runs (6 workers, 6 restarts each) all 100 connection losses were correctly 503, so the window is narrow in normal request flow. The `25P03` path is deterministic, which makes that classification entry ineffective in its natural trigger.
- **Effect.** The user sees "Studio authoring request failed" with no automatic retry, no banner and no Retry now. The command was never sent to PostgreSQL, so there is no commit ambiguity.
- **Integrity.** Held in every case.
- **Correction.** Add `Client has encountered a connection error and is not queryable` and `Client was closed and is not queryable` to the classifier, or rethrow the recorded connection error when pg reports the client unqueryable. On a scratch build, all 17 kill points in the accept `before` mode classified as unavailable (15 unqueryable, 2 `57P01`).

**F4. B — A hung or partitioned database leaves requests waiting without bound; keepalive is inert.** *Demonstrated.*

- **Code.** `POSTGRES_CONNECTION_LIMITS` (`postgres-authoring-store.ts:75-80`) sets `keepAlive: true` without `keepAliveInitialDelayMillis`. Node therefore keeps the OS idle time: 7,200 s on Linux, including the Linode's Ubuntu. No client-side `query_timeout` is set. `statement_timeout` and `idle_in_transaction_session_timeout` are enforced by the server and cannot fire while the server or network is stalled.
- **Reproduction.** (1) `SIGSTOP` on the checked-out backend just before an acceptance statement: the call was still pending after 60 s while other connections were served. (2) A TCP proxy that stops forwarding mid-session: the HTTP request returned nothing within 45 s. With a real partition, only TCP retransmission ends the wait (about 15 min with `tcp_retries2 = 15`).
- **Effect.** The request and the page stay `busy`, and the editor is disabled for the whole wait. Behind staging nginx the browser would get a 504 after 60 s, which the client treats as a non-transient error and not as an ambiguous mutation (see F6).
- **Integrity.** Held. On resume, PostgreSQL's own idle-in-transaction timeout aborted the transaction.
- **Correction.** Add `query_timeout` above the statement timeout (for example 20 s) and `keepAliveInitialDelayMillis` (for example 10 s), and classify `Query read timeout` as unavailable so `inTransaction` discards the client. On a scratch build the frozen acceptance failed at 20 s as `STORE_UNAVAILABLE`, the client was discarded, and nothing committed after resume.

**F5. C — Concurrent Draft/Proposal creation and acceptance deadlock (`40P01`).** Pre-existing since `57f368a`, not introduced by this correction.

- **Cause.** `commitAccepted` locks scope, then project rows `FOR UPDATE` (`:597`, `:623`, `:629`; `transitionProposal` `:556`). Inserts of Drafts and Proposals take foreign-key `KEY SHARE` locks on the same rows in the opposite order.
- **Observed.** 8 in-process workers (propose/accept/reject on two scopes, no restarts): 20 deadlocks against 24 successes. HTTP restart-load runs added 53 deadlocks.
- **Effect.** Each deadlock returns HTTP 500 `STORE_REJECTED`. PostgreSQL aborts one transaction cleanly, so integrity holds.
- **Correction.** `FOR NO KEY UPDATE` in those four statements, which still serializes acceptances. On a scratch build: 0 deadlocks, 949 successful operations, 282 accepted revisions, integrity clean, same-scope races still `CONFLICT`. Consider mapping `40P01`/`40001` to `STORE_BUSY`.
- **Why C.** Rare for single-user M2.5. It becomes B before multi-user use; it is cheap enough to fix with F1–F4.

**F6. C — Gateway errors are neither retried nor treated as ambiguous.** `authoring-retry.ts:70` treats only 503 with a JSON `STORE_UNAVAILABLE` code as transient. An nginx 502 during a Studio restart or 503/504 without that body is a final `HTTP_ERROR` after one request. A 504 on a command that later commits is not reconciled. Treat 502/503/504 as transient, and for commands as ambiguous. Matters for staging behind nginx.

**F7. C — Migration hashes depend on line endings.** The owner's Windows checkout has CRLF in `migrations/001_authoring.sql` (SHA-256 `6849376c…`); the committed LF file used by CI, staging and Linux agents hashes to `a5abdb33…`. A database migrated from one side is refused from the other with "Authoring migration changed". This fails safe. Correction: `*.sql text eol=lf` in `.gitattributes` or normalize line endings before hashing. §12 includes a one-time workaround for `studio_dev`.

**F8. C — Server diagnostics lose the reason for message-classified errors.** Connection terminations, unqueryable clients and malformed stored records are all logged as `code: 'unknown'`, so an operator cannot tell an outage from data corruption. Log the classification and the error name/message for non-SQLSTATE errors; they carry no credentials.

**F9. C — Coverage gaps behind F1–F5.**

- The B1 contention tests use a plain `pg.Pool`, so the new pool bounds are never exercised under contention in CI.
- The V1 regression covers one timing point and no between-queries loss.
- The browser outage test covers only a Save Draft that fails before reaching the server.
- No browser or API test runs Studio in PostgreSQL mode (review item C6).

**D notes.**

- **D1.** The editor is disabled while any request is in flight. That is acceptable for the 6 s retry window, but combined with F4 it blocks editing during a hang.
- **D2.** Accept and restore reconciliation accept an equivalent outcome from another tab as success. This is correct for one principal; durable command ids (deferred) are needed for attribution.
- **D3.** Pool acquisition waits share the 5 s connect timeout, so pool saturation would surface as `STORE_UNAVAILABLE` rather than `STORE_BUSY`. It was not observed even at 100-way contention.
- **D4.** When the connection error arrives after `COMMIT` resolved, `inTransaction` converts a known success into an ambiguous failure. Reconciliation handles this correctly (§5).

## 5. Integrity and lost acknowledgements

Every failure in §4 left PostgreSQL in one of two states: untouched (Proposal pending, head, ChangeSets, checkpoints and current projection unchanged) or fully committed (Proposal accepted with its ChangeSet, revision and checkpoint; head advanced; projection equal to the latest checkpoint). There was no accepted Proposal without history, no history without accepted state, no revision gap, and no duplicate ChangeSet.

Lost acknowledgements were produced with a TCP proxy between Studio and PostgreSQL. It forwards a write `COMMIT` and drops the reply, or never forwards it. The HTTP server and Studio's retry module ran unmodified.

| Case | Client result | PostgreSQL |
| --- | --- | --- |
| Accept, `COMMIT` applied, ack lost | `proposal-accepted` after `getProposal` → `listHistory` → `getRevision`; no resend | 1 ChangeSet |
| Reject, ack lost | `proposal-rejected` via `getProposal`; no resend | Rejected, no history |
| Restore, ack lost | `screenplay-restored` via `listHistory`; no resend | 1 scoped restore |
| Accept, `COMMIT` never applied | Reconcile saw pending → one resend → accepted | 1 ChangeSet |
| Restore, never applied | No matching ChangeSet → one resend → restored | 1 scoped restore |
| Accept, never applied, rival reject before retry | `PROPOSAL_ALREADY_RESOLVED` (not success) | Rejected |
| Reject, never applied, rival accept before retry | `PROPOSAL_ALREADY_RESOLVED` (not success) | Accepted once |
| Restore, never applied, rival same-scope change before retry | `CONFLICT` (not success) | No restore |

Reconciliation only reads (`getProposal`, `listHistory`, `getRevision`, `listProposals`, `listDrafts`) and cannot mutate history.

## 6. `STORE_UNAVAILABLE` and HTTP semantics

| Condition (built server, PostgreSQL mode) | Response |
| --- | --- |
| PostgreSQL stopped (read and mutation) | 503 `STORE_UNAVAILABLE`, `Retry-After: 1` |
| Backend terminated in flight (`57P01`) | 503 |
| Connection lost between queries (unqueryable client, `25P03` path) | **500 `STORE_REJECTED`** (F3) |
| Frozen connection | No response (F4) |
| Stale same-scope Proposal / already resolved / malformed command / missing revision | 200 with `CONFLICT` / `PROPOSAL_ALREADY_RESOLVED` / `INVALID_COMMAND` / `REVISION_NOT_FOUND` |
| Malformed JSON / unsupported method | 400 |
| Missing table (`42P01`), permission denied (`42501`), malformed stored record | 500 `STORE_REJECTED`, no `Retry-After` |
| `40P01` deadlock | 500 `STORE_REJECTED` (F5) |
| After PostgreSQL restart | Next request succeeds on a fresh connection |

The connection URL contained a recognizable password. It appeared in no response body, header or server log line. Bodies are generic; logs contain only the code and request method (see F8). The classifier's unit coverage matches its code; the gaps are the two pg messages in F3 and `Query read timeout` in F4.

## 7. Connection bounds

Server settings are active on real connections: `SHOW statement_timeout` = 15s, `idle_in_transaction_session_timeout` = 30s, connect/acquire timeout 5 s. Refused and dropped connections fail within milliseconds. None of the bounds creates an integrity problem: a timed-out or idle-killed transaction rolls back and the client is discarded. Frozen or partitioned connections are not bounded (F4).

## 8. Client retries and reconciliation

The retry module (`authoring-retry.ts`, compiled unmodified) was driven with a fake transport:

- **Retried:** network failure, `STORE_UNAVAILABLE`, and a command's `STORE_BUSY` result. Each makes 4 requests in total, with sleeps between 375–625, 1125–1875 and 3000–5000 ms. `Retry-After` of 1, 10 and 3600 s gave sleeps of max(1 s, backoff), 10 s and the 60 s cap; an invalid value is ignored.
- **Not retried (1 request):** `CONFLICT`, `INVALID_COMMAND`, `PROPOSAL_ALREADY_RESOLVED`, `REVISION_NOT_FOUND`, 500 `STORE_REJECTED`, 400, and gateway 502/503/504 without a code (F6).

Retries live only in `createRetriedRequest`. `reconcile` uses the single-shot `once`, the page's actions issue requests sequentially, and the server has no connectivity retry, so there is no retry multiplication. The only server loop is B1's `STALE_PROJECT_HEAD` retry in `AuthoringApplication`, which is untouched; a command's `STORE_BUSY` can therefore cost at most 4 × 65 commit attempts, as designed. Ambiguous new Drafts and Proposals are only re-read automatically and resent only after Retry now, as documented.

## 10. No queue or offline semantics

Studio and `v2-core` contain no command queue, browser storage, service worker, background timer or server-side replay; no queue or IndexedDB dependency was added. The only retry state is the in-memory set of ambiguous command keys inside a page session. PostgreSQL remains the single durable authority; the transactional outbox remains deferred.
