## 3. Findings

**V1. High — a checked-out connection dropped by PostgreSQL crashes Studio.** *Demonstrated.*

- **Code.** `createPostgresPool` (`packages/v2-core/src/postgres-authoring-store.ts:750-757`) listens for pool `'error'` events, which pg emits only for idle clients. `inTransaction` (same file, `:66-82`) takes a client with `pool.connect()` and registers no listener on it. When the backend connection ends, pg rejects the active query (the caller sees it) and then emits `'error'` on the client itself. With no listener, Node terminates the process.
- **Reproduction.** Studio wiring (`createPostgresPool` + `PostgresProjectStoreResolver` + `AuthoringApplication`). A second session holds `SELECT … FROM authoring_projects FOR UPDATE`; an `AcceptProposal` blocks inside `commitAccepted`; `pg_terminate_backend` on the waiting backend. Result: `Unhandled 'error' event … Connection terminated unexpectedly` in **10 of 10 runs**. The bare `pool.connect()` / `BEGIN` / query pattern also crashed 10 of 10.
- **Integrity held.** After each of the 11 crashed runs the Proposal was pending, head was 0, and there were no ChangeSets or checkpoints.
- **Triggers.** PostgreSQL restart, failover, network drop, admin termination or `idle_in_transaction_session_timeout` during any store transaction.
- **Correction.** In `inTransaction`, attach an `'error'` listener to the client immediately after `connect()` and remove it before release. When the transaction failed, release with `client.release(err)` so the pool discards the connection. Keep the original error if `ROLLBACK` also fails. Add a PostgreSQL regression test with the reproduction above, asserting that the process survives, the caller receives an error, the Proposal stays pending and the next request succeeds.

**V2. Low — `PROJECT_STATUS.md` says scoped conflicts "stop immediately".** Retries stop at the first attempt after the conflicting change is visible, but before that a losing Proposal can spend several `STALE_PROJECT_HEAD` retries caused by unrelated commits. In 12-way runs with two Proposals on the same document and cut, the loser made 1–9 commit attempts before returning `CONFLICT`. The behaviour is correct; `V2_POSTGRES_PERSISTENCE.md` describes it accurately.

**V3. Low, future work — retries have no backoff.** Each retry restarts `handle()` immediately and re-reads the full head state. Total attempts grow roughly quadratically with concurrent acceptances. With a 10-connection pool: 64 concurrent acceptances took about 16 s (1,149 attempts), 100 took about 51 s (about 2,590 attempts; at most 60 by any one request). All succeeded. Harmless for single-user Studio; add jittered backoff before multi-user load. This also relates to review item C2.

**V4. Low — contract failures identify the backend only by CI step or config.** Test titles are identical in both runs. The CI step names ("(in-memory)", "(PostgreSQL)") and the vitest config identify the backend, which is adequate.

## 9. Decision — database connectivity failures

Owner decision, Sep 26, 2026, taken after V1. Network drops and database restarts can last minutes. Studio must survive them, tell people what is happening, keep their unsaved work and let them retry.

**Alternatives considered and rejected.**

- *Server-side RAM queue of pending commands.* Volatile: a process restart, including one caused by a connection error, loses exactly the work it was meant to protect.
- *Redis queue.* Durable, but a large additional dependency and a second durable store. Every queued command would need an exactly-once handoff into PostgreSQL, reintroducing the dual-write problem.
- *Either queue.* Replaying a queued acceptance later applies a human decision to a state the person never saw. PostgreSQL remains the single source of truth; a queue is only appropriate for asynchronous side effects, through the deferred transactional outbox in PostgreSQL.

**Server policy.**

1. Never crash on connection loss: pool-level handler (done) plus client-level handling in `inTransaction` (V1).
2. Fail fast with a distinct retryable result: connectivity failures (connection refused or reset, connect or statement timeout, SQLSTATE class `08`, `57P01`–`57P03`) return HTTP 503 with code `STORE_UNAVAILABLE` and a `Retry-After` header. Other thrown errors are logged server-side with their code and return a non-retryable error (review item C3).
3. Bound waiting: set `connectionTimeoutMillis`, `statement_timeout`, `idle_in_transaction_session_timeout` and TCP keepalive on the pool (review item C8). Suggested starting values: 5 s, 15 s, 30 s.
4. Optional fast-fail flag: a periodic `SELECT 1` marks the store unavailable so requests during a long outage fail at once instead of each waiting out the connect timeout.
5. No reconnect loop (the pool opens fresh connections on demand) and no automatic replay of write transactions.

**Client policy.**

1. **Three automatic retries** after the first attempt, at about 0.5 s, 1.5 s and 4 s with ±25% jitter, using the server's `Retry-After` when it is longer. The UI shows "Reconnecting… (attempt n of 3)".
2. Retry only transient results: network failure, `STORE_UNAVAILABLE`/503 and `STORE_BUSY`. Never retry `CONFLICT`, `INVALID_COMMAND`, `PROPOSAL_ALREADY_RESOLVED`, `STORE_REJECTED` or validation errors.
3. Reads and `SaveDraft` (a conditional upsert by Draft id) are always safe to retry. `CreateProposal` may retry automatically once a repeated request cannot create a second Proposal; confirm or add that guarantee.
4. Accept, reject and restore use the same three retries, but reconcile before reporting failure. After a retried attempt, `PROPOSAL_ALREADY_RESOLVED` or a restore `CONFLICT` may mean an earlier attempt succeeded. The client re-reads the Proposal or history and reports the actual outcome.
5. After the third failed retry, show a persistent banner stating that the database cannot be reached and that the unsaved work is kept in this browser, with a **Retry now** action. After reconnection, re-read state before showing results.

**Scope.**

- *Before M2.5 acceptance:* V1 fix and regression test; `STORE_UNAVAILABLE` classification; pool timeouts; three client retries with the banner and manual retry.
- *Next Studio milestone:* mirror unsaved edits to IndexedDB so they survive a reload or closed tab; a client-generated id per command, stored with the ChangeSet under a unique constraint, so a retry after a lost acknowledgement returns the original result instead of `PROPOSAL_ALREADY_RESOLVED` or `CONFLICT` (replaces the constant `request:studio-write`; review item C3).
