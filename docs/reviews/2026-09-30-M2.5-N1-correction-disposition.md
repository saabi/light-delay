## Root cause and correction

A pg query-read deadline abandons the JavaScript wait without necessarily
cancelling PostgreSQL work. A COMMIT already sent can complete after the caller
receives `STORE_UNAVAILABLE`. The first reconciliation can still see pending
state. The resend then waits behind the original's row lock and, after the
original commits, returns `PROPOSAL_ALREADY_RESOLVED` or restore `CONFLICT`.
The previous retry helper returned that semantic failure without another read.

The helper now performs one additional reconciliation when an ambiguous command's
resend returns `ok: false`, after the existing `STORE_BUSY` handling. It replaces
the response only when reconciliation returns `ok: true`. If the intended outcome
is absent or incompatible, the original resend error is preserved, including its
message. Semantic failures without preceding infrastructure ambiguity still return
immediately. The existing bounded retry budget and manual-retry policy are unchanged.

The existing authoritative checks remain the evidence:

| Command | Required evidence |
| --- | --- |
| AcceptProposal | Exact Proposal accepted, its referenced ChangeSet exists, and its resulting ProjectRevision exists |
| RejectProposal | Exact Proposal rejected |
| RestoreScreenplay | Scoped-restore ChangeSet matches target revision, document/cut scope and expected document version, with a resulting ProjectRevision |
| CreateProposal | Exact stable Proposal ID and matching source Draft, unchanged |

A document-version increase alone is insufficient. A rejected Proposal cannot
confirm acceptance; an accepted Proposal cannot confirm rejection. Ordinary
same-scope writes cannot confirm a restore. Attribution of equivalent outcomes
from another tab remains the previously documented D2 deferral; this pass adds
no heuristic and no generalized command identity.

## Exact PostgreSQL regression

`packages/v2-core/test-support/postgres-fault-proxy.ts` is a test-only loopback,
non-TLS PostgreSQL wire proxy. It parses complete frontend protocol messages,
forwards all mutation SQL, and holds exactly one write transaction's real COMMIT
bytes and the subsequent client EOF. pg's actual 500 ms `query_timeout` fires;
the production deadline remains 20 seconds. No mutation, transaction result or
semantic response is mocked.

For each positive case, the test records real unavailability, the pre-resend
pending/history read, and an actual PostgreSQL lock wait visible in
`pg_stat_activity`. Only then does it release the original COMMIT. The resend's
real semantic failure is recorded separately from the retry helper's reconciled
success.

| Case | Resend | Final result | Persistence |
| --- | --- | --- | --- |
| Accept | PROPOSAL_ALREADY_RESOLVED | proposal-accepted | 1 terminal transition, 1 accepted ChangeSet/revision/checkpoint, head/version 1, intended text |
| Reject | PROPOSAL_ALREADY_RESOLVED | proposal-rejected | 1 terminal transition, no accepted history/checkpoint, head/version 0, original text |
| Restore | CONFLICT | screenplay-restored | 1 restore ChangeSet/revision/checkpoint following the seed acceptance, head/version 2, original content |

Negative cases discard the captured original COMMIT after its real query deadline
and pending/history read, then establish an incompatible competing outcome before
the resend. Accept loses to rejection; Reject loses to acceptance; Restore loses
to a different same-scope accepted edit. All three preserve the resend's genuine
semantic failure. No scoped restore appears in the negative restore history.

Each case queries persistence directly: a test-only trigger counts terminal
Proposal transitions; SQL checks revisions against ChangeSets, head, checkpoints,
scoped versions and current projection; accepted-history export is checked too.
No duplicate or partial mutation was found. The same three positive tests fail
against the unmodified starting retry helper, reproducing N1; they pass with the
correction. The negative tests also pass.
