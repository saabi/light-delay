# Studio M2.5 PostgreSQL Persistence — Independent Review

Sep 25, 2026 · @Sebastian Ferreyra

Review of `saabi/light-delay` branch `implementation/m2.5-postgres` at `7f28dc8` against accepted M2 `c0881311`. Read-only: nothing was modified, committed, merged, migrated remotely or deployed. All probes ran against a disposable local PostgreSQL 16.13 and were deleted afterwards.

## 1. Executive verdict

**M2.5 is sound after bounded corrections.** There is no A finding. The persistence of authoritative state and history holds up under adversarial concurrency, injected failure, a lost commit acknowledgement, restart and differential reconstruction. Two B findings must be fixed before acceptance or deployment. A third B finding is a cheap evidence gap against the milestone's own exit criteria.

What holds, with evidence:

- **Linearizable acceptance.** Every write to authoritative tables happens while holding the project row lock. Validation reads happen after that lock is taken, so `READ COMMITTED` is correct here.
- **Exactly one terminal transition.** Tested 40 rounds each of accept‖reject, accept‖accept and reject‖reject on separate connections. Persisted status always matched the winner.
- **Consistency under mixed stress.** A 12-wave mixed run (accept, restore, reject, Draft, Proposal) over 6 scopes produced zero deadlocks, zero duplicate history and zero current/checkpoint divergence. Full history replay passed.
- **Contract parity with in-memory M2.** The unchanged M2 authoring contract suite (36 tests) passes against the PostgreSQL adapter. An 11-revision differential run (insert, text, move, removal, restore, sibling cut, second document) matched in-memory M2 exactly: every revision, every scoped view, the ChangeSet list and the accepted-history export.
- **Scoped storage preserved.** Each revision stores 1 ChangeSet (\~1.5 KB), 1 metadata row (\~0.3 KB) and 1 checkpoint per touched scope. The whole project is never stored per revision.

What must change:

- **B1: unrelated-scope acceptances falsely fail at 5 or more concurrent commits.** The application retries a stale global head only 3 times, then reports `STORE_REJECTED`. With k concurrent accepts on k distinct documents, exactly 4 succeed: 2 of 6 fail, 4 of 8 fail, 12 of 16 fail. State stays correct and Proposals stay pending, but M2's scoped-concurrency property holds only up to 4 concurrent commits.
- **B2: a dropped idle database connection crashes Studio.** `createPostgresPool` registers no `pool.on('error')` handler. Terminating one idle pooled backend killed the built Studio server running in PostgreSQL mode.
- **B3: the milestone's parity criterion is not in CI.** The roadmap's own M2.5 exit criterion is "equivalent application contract tests pass against in-memory and PostgreSQL adapters". The branch ships a separate 26-test suite instead. I showed parity by hand; CI does not keep it true.

The relational model is a faithful persistence representation of M2, not a competing domain model. The one structural caveat for the future is D1: documents, cuts and the scope list are currently read from the revision-0 JSON. Fixing that later is additive.

## 3. Persistence architecture reconstructed

The adapter is a thin relational envelope around TypeBox-validated JSON records. Every M2 invariant is still decided by the M2 pure functions: `projectAuthoringOperations`, `validateAcceptedMutation`, `validateProjectProjection` and `validateRestoreReferences`. SQL keys add backstops: no duplicate revision, no duplicate ChangeSet, a Proposal cannot be accepted without a ChangeSet, and scope and element identity are unique.

| Concern | What exists in the code |
| --- | --- |
| Client / pool | `pg` 8.23 (node-postgres). `createPostgresPool(url)` = `new Pool({connectionString})`, which defaults to max 10. There is **no `error` listener**, no statement or idle-in-transaction timeout, and no connect timeout. |
| Transaction helper | `inTransaction(pool, fn)`: connect, `BEGIN`, fn, `COMMIT`; `ROLLBACK` on throw; release. Error *results* return before any write, so they commit empty transactions (checked). Reads use `REPEATABLE READ READ ONLY`. |
| Migrations | A custom runner in one transaction under `pg_advisory_xact_lock`. It applies `^\d{3}_[a-z0-9_]+\.sql$` in lexical order and records SHA-256 in `authoring_schema_migrations`. It fails on a changed or unknown applied migration. Run via `npm run migrate:studio`, **never at startup**. |
| Projects | `authoring_projects`: `initial_revision` jsonb (full revision-0 state), `head_number`, `history_contract_version` (default 1). |
| Identities | `authoring_documents` (with `kind`, always `'screenplay'`, never read back), `authoring_versions` (cuts, project-wide), `authoring_elements` (registry: PK project + element, document FK, `kind` CHECK over the 4 screenplay kinds, `created_in_revision`). |
| Current state | `authoring_scopes` (PK project, document, version): `document_version` + `content` jsonb `{order[], elements[]}`, where removed elements are kept as tombstones. |
| History | `authoring_revisions` (PK project + number; metadata record), `authoring_change_sets` (record + `schema_version` column; unique revision), `authoring_checkpoints` (PK project, revision, document, version; full content of each **touched** scope). |
| Drafts | `authoring_drafts`: scope, owner and base columns plus the full record. Saving is one conditional upsert that can change only `record` while scope, owner and base columns are unchanged. |
| Proposals | `authoring_proposals`: `status` CHECK pending/accepted/rejected, `change_set_id` FK, `CHECK ((status='accepted') = (change_set_id IS NOT NULL))`, full record. |
| Revision allocation | The app computes `head+1` from a snapshot. Inside the transaction the store requires `baseRevision = locked head`. The revision number is the PK, with no sequence. The ChangeSet id (`changeset:<uuid>`) is separate from the revision number. |
| Accept transaction | Lock the Proposal `FOR UPDATE`, then the touched scopes `FOR UPDATE` (sorted), then the project row `FOR UPDATE`. Then run a full `readState(head)`, the head check, the duplicate check, restore-target validation, the M2 reducer and `validateAcceptedMutation`. Then insert the revision, ChangeSet, new element rows and checkpoints; update scopes; update head; set Proposal accepted `WHERE status='pending'`; `COMMIT`. |
| Historical read | Uses the latest checkpoint at or before N for each scope (`DISTINCT ON`), otherwise the initial projection. Elements come from `created_in_revision <= N`. **Documents, cuts and the scope list come from `initial_revision`.** |
| Current read (7f28dc8) | One `REPEATABLE READ` query for the scope row joined to project, document and version, plus a registry lookup of that scope's element ids. |
| Server boundary | SvelteKit `POST /api/authoring` with a method allowlist. `handle` always receives the server constant `{principal: user:local-filmmaker, requestId: request:studio-write}`. The app is created lazily; production defaults to PostgreSQL. The Harbor Light fixture is seeded on first use. |
| Test DB | `TEST_DATABASE_URL`; a random schema per run, migrated in `beforeAll`, `TRUNCATE … CASCADE` between tests, `fileParallelism: false`, pool max 10. |
| CI | `postgres:16` service with trust auth; `migrate:studio` then `test:postgres` in the Studio job. No other workflow touches a database. |

**Discrepancies with the implementation report and docs:**

1. **The project lock is not held "briefly".** It is held from after the scope locks until `COMMIT`. That window covers a full-project read, the O(n²) M2 validation and all writes, about 0.5 s at 1 screenplay × 3 cuts × 2,000 elements. That lock, not the scope locks, is what linearizes acceptance. The scope locks are redundant for correctness.
2. **The accept order in the brief is only approximate.** The revision number is chosen *before* the transaction, and the store checks global head equality. Inside the transaction the order of writes is irrelevant.
3. **"Without a false document conflict" holds only up to 4 concurrent commits (B1).**
4. **The "migrates an empty schema" test only asserts the rerun.** The fresh migration happens in `beforeAll`, without assertions.

## 4. Findings

### A — M2.5 blockers

None. No interleaving, injected failure or lost acknowledgement I could construct corrupted or contradicted authoritative state or history.

### B — Fix before acceptance / deployment

**B1. Unrelated-scope acceptances falsely fail at 5 or more concurrent project commits.** *Reproducible concurrency anomaly.*

- **Evidence.** k Proposals on k distinct documents were accepted with `Promise.all`, each on its own app and connection:

  | k | Succeeded | Failed with `STORE_REJECTED: Project head advanced before commit` |
  | --- | --- | --- |
  | 2 | 2 | 0 |
  | 4 | 4 | 0 |
  | 6 | 4 | 2 |
  | 8 | 4 | 4 |
  | 16 | 4 | 12 |

  In the mixed stress run, 19 of 142 outcomes were this same error.
- **Code.** `authoring.ts` AcceptProposal and Restore: `if (!stored.ok && stored.code === 'STALE_PROJECT_HEAD' && retryCount < 3) return this.handle(...)`. The next line maps anything else to `STORE_REJECTED`. The store checks `mutation.changeSet.baseRevision !== current.number`.
- **Interleaving.** All k callers read head h and build ChangeSets with `baseRevision = h`. They queue on the project row. One commits h+1, and k−1 get `STALE_PROJECT_HEAD` and retry against h+1. One wins per round, so after 4 attempts exactly 4 have won.
- **Consequence.** No corruption: the loser's Proposal stays pending, and nobody is told a false success. But a document-scoped acceptance fails because of unrelated work, with an error that looks like a rejection, not a transient. That contradicts the M2 property and the PG test's name. Future agent or bulk acceptance makes k ≥ 5 realistic.
- **Why B, not A.** Authoritative state is never wrong. The failure is visible and retryable. It needs 5+ simultaneous commits in one project, which today's single-user Studio will not produce.
- **Smallest correction.** Treat `STALE_PROJECT_HEAD` purely as a retry signal. Every stale result proves another commit succeeded, so the system as a whole always progresses. Loop until success or a semantic outcome (`CONFLICT`, already resolved), with a generous cap (e.g. 25) and a few ms of jittered backoff. Map exhaustion to a distinct retryable code, not `STORE_REJECTED`. Add a PG test with k ≥ 8 unrelated accepts. The larger alternative is to allocate the revision inside the locked transaction; it is not needed now.

**B2. A dropped idle connection crashes the Studio process.** *Demonstrated.*

- **Evidence.** `createPostgresPool` returns a `Pool` with no `'error'` listener. I ran the built Studio in `STUDIO_AUTHORING_STORE=postgres` mode, made requests, then ran `pg_terminate_backend` on its idle backend. Node exited with `Unhandled 'error' event … Emitted 'error' event on BoundPool instance`, and the next request got connection refused. A standalone script reproduces the same crash.
- **Consequence.** Any PostgreSQL restart, failover, maintenance, admin kill or network idle drop takes Studio down.
- **Correction.** In `createPostgresPool`, add `pool.on('error', …)` that logs the error code without connection details. Also consider `idle_in_transaction_session_timeout` and `statement_timeout` at pool level.

**B3. The parity exit criterion is not in CI.** *Evidence gap, not a known bug.*

- **Evidence.** The baseline roadmap's M2.5 exit criterion reads "equivalent application contract tests pass against in-memory and PostgreSQL adapters". The branch adds a separate 26-test PG suite instead. I ran the unchanged M2 `authoring.test.ts` against PG by changing only its harness: a fresh migrated schema per harness, with `forProject` pinned to one store instance so the spies attach. **36/36 passed.**
- **Consequence.** Parity is true today but nothing keeps it true. The in-memory adapter and the SQL adapter can drift silently.
- **Correction.** Parameterize `createHarness` over both adapters, and run the PG variant in the `test:postgres` job.

### C — Address during staging / next persistence iteration

**C1. An acceptance blocks every new Draft and Proposal in the project.** *Demonstrated.* `SELECT … FROM authoring_projects … FOR UPDATE` (and scope `FOR UPDATE`) conflicts with the `FOR KEY SHARE` taken by the foreign-key checks when a Draft or Proposal row is inserted. While a session held the project lock, a Draft insert *in a different document* hit `lock_timeout`. Fix: use `FOR NO KEY UPDATE` for both lock sites. That keeps mutual exclusion between acceptances and stops blocking FK readers.

**C2. The serialization window is dominated by inherited M2 validation.** At 1 screenplay × 3 cuts × 2,000 elements, the store holds the project lock for about 0.5 s per acceptance, and end-to-end accept takes about 1.05 s. At 3 × 3 × 2,000, accept takes 2.8–4.7 s. The cost is mostly M2 pure-function O(n²) lookups (`find` and `includes` inside `validateProjectProjection` and `validateScopeContent`). In-memory accept takes 0.55 s and 2.5 s at the same sizes. PG runs the validation twice, once in the app and once in the store. Fine at Studio scale. Replace the linear lookups with Map/Set lookups in M2 code; this also narrows B1's window.

**C3. Error mapping and observability.** The route turns every thrown error into HTTP 503 "temporarily unavailable" and **logs nothing**. Integrity failures ("Stored authoring record is malformed", "Proposal transition lost its lock", constraint violations) look the same as an outage. After a lost commit acknowledgement, a retried accept gets `PROPOSAL_ALREADY_RESOLVED` without the ChangeSet id. Recovery is possible but indirect, via `getProposal().changeSetId`. `requestId` is the constant `request:studio-write`, so it correlates nothing. Recommendations:

- Log server-side with error codes.
- Return `{code: PROPOSAL_ALREADY_RESOLVED, status, changeSetId}` so a retrier can tell "mine won" from "rejected" without being told a false success.
- Mint a per-request `requestId` on the server.

**C4. Studio page load reads unbounded collections.** Each page load fetches all Drafts (full element arrays, all owners), all Proposals (including resolved ones, with full operations) and the whole ChangeSet history. Restore ChangeSets embed full scope content. This grows without bound. Add filtered and paged reads: pending Proposals, the caller's Drafts, and recent history metadata.

**C5. History access paths.** The historical `DISTINCT ON` scans every checkpoint at or before N for the project. That is cheap today because only TOAST pointers are sorted. Add an index on `(project_id, document_id, version_id, revision_number DESC)` when revisions reach the thousands. `exportAcceptedHistory` replays everything through `fromAcceptedHistory`: **45 s for 120 revisions** at 1 × 3 × 2,000, inside one `REPEATABLE READ` snapshot. Only tests call it today. It is not viable as a backup or export path at scale until replay uses checkpoints or C2 is fixed.

**C6. PG test gaps (details in §13).** The unrelated-scope test uses k = 2, which hides B1. accept‖reject does not assert persisted status against the winner. The scale test does not measure checkpoint size. Studio e2e is pinned to memory mode, so no browser or API test touches PostgreSQL. The Draft-base test advances a *different* document.

**C7. Duplicated fields with no tie constraint.** `authoring_proposals.status` duplicates `record.status`: `commitAccepted` reads the column and `transitionProposal` reads the record. `authoring_change_sets.schema_version` is written but never read; readers use `record.schemaVersion`. Draft base columns duplicate `record`. All are consistent while only this adapter writes. Add `CHECK (status = record->>'status')` and `CHECK (schema_version = (record->>'schemaVersion')::int)`, or read the column.

**C8. Staging hygiene.** Production mode seeds the Harbor Light fixture into whatever `DATABASE_URL` points at on first request. That is acceptable only while the fixture is the sole project. There is no pool timeout configuration. The docs already require an access boundary before real authoring.

### D — Later architectural / operational work

- **D1. Structure is read from revision 0.** `readState` takes `documents`, `versions` and the list of scopes from `authoring_projects.initial_revision`, not from `authoring_documents`, `authoring_versions` or `authoring_scopes`. The relational identity tables are write-only mirrors today. Adding a cut or document later (Festival cut, Outline) means making those tables authoritative and adding `created_in_revision` to them for historical reads. That is additive (§11).
- **D2. Checkpoint granularity.** Each revision stores the full touched scope: \~427 KB raw JSON at 2,000 elements, 26 KB after TOAST compression on synthetic text. Real prose will compress less. Growth follows revisions × scope size, not project size. Sparse checkpoints (every k revisions + replay) are an option if needed.
- **D3. Scope narrowed by the implementation.** The outbox and minimal authorization were removed from M2.5 in a doc edit and need owner sign-off. Both remain additive: an outbox table written in the same transaction; authorization at the route plus a project-membership table.
- **D4. Freeze v1 record schemas.** Stored rows are re-validated against today's TypeBox v1 schemas on every read. Any later tightening of v1 (length limits, patterns) would make old rows unreadable. Changes must go to v2 with dispatch.
- **D5. Owner-scoped reads.** `listDrafts` returns every owner's Drafts. This becomes relevant once authentication exists.

## 5. Transaction and concurrency analysis

**`READ COMMITTED` is correct. Stronger isolation would not help and would add failure modes.** The project row lock acts as a per-project mutex. Every statement that writes `authoring_scopes`, `authoring_elements`, `authoring_checkpoints`, `authoring_revisions`, `authoring_change_sets` or `head_number` runs inside `commitAccepted` after taking that lock. The only exception is `seedProject`, which runs only for a project row that does not exist yet. Under `READ COMMITTED`, each statement after the lock sees a fresh snapshot, and no other writer can commit until this one releases. So the head check, the document-version precondition in the M2 reducer, the element-kind check and the restore-target check all run against the latest committed state, and that state cannot change before `COMMIT`.

`REPEATABLE READ` would take its snapshot at the first statement, which is the Proposal lock *before* the wait. Later reads would then see a stale head, and `FOR UPDATE` on a row changed meanwhile would raise `40001`. `SERIALIZABLE` would add aborts without preventing any anomaly that exists here.

| Question | Answer |
| --- | --- |
| Rows locked, in order | 1. Proposal (accept only). 2. Touched scopes, sorted by (documentId, versionId). 3. Project row. All `FOR UPDATE`. Reject locks only the Proposal. |
| Reads relative to locks | Head, scopes and registry are read after all three locks are held. The app-side ChangeSet is built from an earlier snapshot and fully re-validated in the store. |
| Missing scope row | Returns `INVALID_ACCEPTED_MUTATION "Unknown screenplay scope"` before any write. Scope rows are created only by seeding, so there is no phantom case. |
| Overlapping or partially overlapping scopes | Today every Proposal and Restore touches exactly one scope. Multi-scope operations would lock in sorted order. The project lock serializes regardless. |
| New-row phantoms | Element rows are inserted under the project lock, with the PK `(project_id, element_id)` as a backstop. Tested: same new id, conflicting kinds, two cuts, concurrent, 15 rounds. Exactly one succeeded each time, with one registry row. |
| Document-version check vs concurrent modification | Protected: it is evaluated by the reducer against the post-lock read. |
| Proposal terminal transition | Protected: row lock, `status='pending'` check, conditional update, and a thrown error if the update touches 0 rows. |
| Duplicate accepted history | Impossible: Proposal lock + status, `UNIQUE(project, change_set_id)` on proposals and ChangeSets, `PK(project, number)` on revisions, and the contiguity check. |
| Writes outside the transaction | None for accepted state. Draft and Proposal creation are single autocommit statements by design. |
| Current state vs history divergence | Impossible within the adapter: both are written from the same validated checkpoint objects in one transaction. After stress, the latest checkpoint equalled the current row for every scope; divergent rows = 0. |

**Accept / reject races.** 40 rounds of each pattern, with separate app instances and connections:

| Race | Result |
| --- | --- |
| accept ‖ reject | Exactly one winner every round (1 accept won, 39 reject won). Loser got `PROPOSAL_ALREADY_RESOLVED`. Persisted status always matched the winner. The accepted `changeSetId` matched the winner's ChangeSet. |
| accept ‖ accept | One success every round; history +1 per round. |
| reject ‖ reject | One success every round; no history. |

After all 120 races, head = ChangeSets = 41 and accepted Proposals = acceptance ChangeSets = 41. Full replay passed.

**Stale same-scope Proposal.** Returns `CONFLICT "Document version changed from N to N+1"` both in the suite and in stress (14 occurrences), and it is never retried. Correct.

**Unrelated scopes.** Global history is totally ordered, and the *semantic* precondition is correctly document-scoped: global head movement never leaks into `DocumentVersionEquals`. But global head equality is also a mechanical store precondition, and it is retried only 3 times. That produces B1.

**Lock ordering and deadlocks.** The order is always Proposal → sorted scopes → project. The other lockers are Reject (Proposal only) and Draft/Proposal inserts (FK `KEY SHARE` on the project and scope, single statement, no further waits). There is no cycle. Mixed stress across 6 overlapping scopes, with concurrent accept, reject and restore on the same scopes, produced 0 deadlocks. The cost of this design is availability (C1), not correctness.

**Revision allocation.** The ordering is deterministic. The number is `head+1`, the PK is `(project_id, number)`, and there is no sequence. Rollback leaves no gap, and gaps cannot occur because `validateAcceptedMutation` requires contiguity. Revision identity is `(project, number)`; the ChangeSet id is distinct. Projects never interfere because the lock is per project row. Contiguity (`baseRevision = head`) is stronger than the semantics require, which is why B1 exists. But it is inherited from the M2 contract, so relaxing it is not an M2.5 change.

**Retry after an ambiguous commit.** I simulated `COMMIT` succeeding and the connection error arriving afterwards.

| Failure point | Outcome |
| --- | --- |
| Before `BEGIN` | Nothing written; a retry proceeds normally. |
| After locks, before writes | An error result is returned and an empty transaction commits. Nothing written. |
| After partial writes | Throw, then `ROLLBACK`. The suite's injected trigger test shows Proposal still pending, head 0, no history. |
| During or after `COMMIT`, response lost | The first caller gets an exception (503 in Studio). A retried accept gets `PROPOSAL_ALREADY_RESOLVED`. History length is 1. `proposal.changeSetId` equals the committed ChangeSet, so the link is recoverable. |
| Restore retry after lost response | `CONFLICT "Document version changed from 1 to 2"`. No duplicate, but misleading (C3). |

Proposal identity plus status gives sufficient retry safety for M2.5. No general idempotency framework is needed.

## 6. Schema and migration review

**The relational model persists M2; it does not redefine it.** JSON records hold the TypeBox-authoritative representation. Relational columns exist for keys, lookups and backstops. The one structural exception is D1: the project structure lives in the revision-0 blob.

**Constraints, and whether they match the runtime:**

| Constraint | Runtime equivalent | Verdict |
| --- | --- | --- |
| `revisions.CHECK((number=0 AND change_set_id IS NULL) OR (number>0 AND change_set_id IS NOT NULL))` | Revision 0 has null ChangeSet | Consistent |
| `proposals.CHECK((status='accepted') = (change_set_id IS NOT NULL))` + FK to ChangeSets | Accepted Proposal has `changeSetId` | Consistent; stronger than the record alone |
| `elements.kind IN (4 kinds)` | `ScreenplayElementKindSchema` | Consistent now. Adding a kind in TypeBox without a migration means the **runtime accepts and the DB rejects** (loud; the tx rolls back). Acceptable. |
| `documents.kind ~ '^[a-z][a-z-]*$'` | Not modeled at runtime | DB-only, always 'screenplay'. Harmless, and a useful seam. |
| IDs are plain `text` | ASCII pattern, ≤ 32:128 | The DB accepts ids the runtime rejects. Only reachable via manual SQL, and reads then throw "Stored authoring record is malformed". Acceptable. |
| Revision / version numbers are `bigint ≥ 0` | Safe integers | Consistent. `Number()` conversion is safe below 2^53. |
| Timestamps as strings inside jsonb | `persistedInstantFormat` | Canonical UTC form preserved byte-for-byte; no `timestamptz` conversion. An invalid clock value is rejected before persistence (`INVALID_DRAFT`). |
| Text in jsonb / `text` | Pattern rejects NUL and lone surrogates | Rejected at the command boundary (`INVALID_COMMAND`) before SQL, so the PG jsonb errors are unreachable through the app. |
| Duplicated status / schema\_version / base columns | Record fields | No tie constraint (C7). |

**Migration mechanism.** Verified end to end:

- **Fresh database:** an empty schema gets the current schema (11 tables).
- **Rerun:** a no-op.
- **Four concurrent migrators:** all succeed, serialized by the advisory lock.
- **Checksum drift:** "Authoring migration changed".
- **Unknown applied version:** "Unknown applied authoring migration".
- **Pre-existing unmanaged table:** fails loudly ("relation already exists"), so the runner never silently adopts it.
- **Transactional:** a failed migration leaves nothing behind (PostgreSQL DDL is transactional).
- **No `IF NOT EXISTS` strategy:** only the tracking table uses `IF NOT EXISTS`.
- **No automatic execution:** migrations never run on Studio startup or from tests against a configured URL. Tests use `TEST_DATABASE_URL` and a random schema.

Future procedure: add `002_….sql` and never edit `001`. One limitation to keep in mind: every migration runs in the runner's single transaction, so a future `CREATE INDEX CONCURRENTLY` cannot use it without a runner change. That is acceptable at this scale.

**Accepted-history contract version vs schema version: independent.** They live in three separate places:

- Schema version: `authoring_schema_migrations` (filenames and checksums).
- History contract version: the `authoring_projects.history_contract_version` column. It is checked in `readState` and the current view; anything other than 1 fails with "Unsupported accepted history contract version: N" (suite-tested).
- ChangeSet operation version: `record.schemaVersion`. It dispatches through the M2 `acceptedReducers` and `acceptedHistoryReaders` maps; 99 fails clearly (suite-tested).

A physical migration does not touch the contract version, and a contract bump does not require DDL. Historical records are never pushed back through command validation. Rehydration uses record schemas and reducers. Note D4: v1 record schemas must be frozen.

**Index sufficiency.** Every access path listed in the brief has a covering PK or unique index: current scope, Draft, Proposal, terminal transition, revision list (`UNIQUE(project_id, revision_number)`), restore-target lookup and element validation. The only index I would add at scale is the per-scope checkpoint index (C5). Proposal listing lacks a status filter (C4), but that is a query-shape issue, not an index issue.

## 7. Durability and reconstruction

**Everything survives a restart and reconstructs to the state that was authoritative at each revision.** The store keeps no in-process state beyond the pool and project id. Every test and probe used a fresh resolver and store per call, so "restart" is real for this adapter.

| Object | Verified |
| --- | --- |
| **Draft** | Tested N → save → reload → *same scope* advances to N+1 by another principal → naive resave with base N+1 is **refused** (`INVALID_DRAFT`) → resave with base N succeeds → reload → propose. Base stays `(rev 0, docVersion 0)`. Owner, scope and `createdAt` are preserved. Only 2 revisions exist: revision 0 plus the other acceptance, so Draft saves created none. The Proposal holds **one** operation, relative to N, with precondition `expectedDocumentVersion: 0`, and acceptance returns `CONFLICT`. The SQL upsert also enforces this: `ON CONFLICT … DO UPDATE SET record … WHERE` scope, owner and base columns are equal. |
| **Proposal** | After reload, identity, scope, operations, preconditions, `proposedBy`, `source.contentAuthors`, `source.generator` and pending state are equal to the originals (suite, plus a differential run). |
| **Current projection** | Equal to in-memory M2 for every scope after 11 mixed revisions. Current rows equal the latest checkpoints after stress. |
| **ChangeSets** | `listHistory` from PG is deep-equal to in-memory M2 (differential run, deterministic ids and clock). |
| **ProjectRevisions** | Metadata only: about 298 bytes each, with touched scopes, ChangeSet id and timestamp. |
| **Checkpoints** | Exactly one per touched scope per revision. After 120 revisions on one scope there were 120 checkpoint rows, and none for untouched cuts or documents. |
| **Historical reconstruction** | `getRevision(r)` and `getScreenplayView(scope, r)` for r = 0…11 over 4 scopes were deep-equal to in-memory M2. The script covered insert, text revision, move, removal in a sibling cut, a second document, removal of an inserted element, re-insertion of the same id in another cut, 2 restores (one to rev 2, one to rev 0), and an edit after restore. No off-by-one: the checkpoint at r is used for r, never r−1 or r+1. |
| **Accepted-history export** | PG export is deep-equal to the in-memory M2 export. `fromAcceptedHistory(pgExport).getHead()` equals the PG head. |
| **Restore** | Tested in the suite, the differential run and stress. Added elements disappear from the visible view; they stay in the registry and the scope becomes `unknown` for them. Removed elements return and wording returns. Order returns exactly (id arrays compared). The sibling cut and the unrelated document are unchanged. Provenance is `scoped-restore` with target revision, target document version and scope, and the principal is the trusted accepter. A new revision is appended. It is atomic in the same transaction path as acceptance. Restore racing acceptance on the same scope: the document-version precondition decides, as in stress (no divergence, no duplicate). |

**The one gap is historical enumeration of structure.** The historical path uses `initial_revision` for documents, cuts and the list of scopes (D1). That is correct today, because M2 has no operation that creates a document or cut.

## 8. Provenance and authority

**Authorship and acceptance authority stay distinct and survive round trips. Neither the browser nor a stored Proposal can supply authority.**

- **Alice authors, Bob accepts.** The permanent ChangeSet has `principal = user:bob` (the accepter, from trusted context) and `provenance = {kind: proposal-acceptance, proposalId, proposedBy: user:alice, contentAuthors: [user:alice], source.generator.principal: system:deterministic-draft-diff}`. The accepted Proposal record has `resolvedBy = user:bob`. Verified in the suite and in a probe.
- **Forged command fields.** An `AcceptProposal` carrying `principal` or `timestamp` is rejected as `INVALID_COMMAND` ("principals, timestamps, accepted IDs, and provenance are trusted runtime data").
- **Tampered stored Proposal.** I injected `resolvedBy: user:mallory` into a pending record via SQL. The next read threw "Stored authoring record is malformed". Nothing was accepted, and nothing forged reached history.
- **Store-level checks.** `commitAccepted` requires that the accepted Proposal equals the stored pending Proposal apart from resolution fields; that `resolvedBy` equals `changeSet.principal`; and that operations and preconditions equal the stored Proposal's. The accepter, timestamp and ChangeSet id come only from the app (server clock and id factory).
- **Not checked by the store:** `changeSet.provenance` against the stored Proposal. Only trusted server code builds it, so this is not a forgery path. A future non-app caller of the store would need that check.
- **Studio route.** `handle` ignores any browser-supplied second argument. A live request with `{principal: user:mallory}` produced a Draft owned by, and a ChangeSet accepted by, `user:local-filmmaker`.

**Trusted timestamps.** Timestamps are generated server-side and stored as canonical UTC strings. `revision.timestamp` must equal `changeSet.timestamp`.

## 9. Identity and cut/version semantics

**Element identity and kind are stable per project, across cuts, restore, rehydration and concurrency.** The registry is `authoring_elements` with PK `(project_id, element_id)`, a document FK, a `kind` CHECK and `created_in_revision`. The M2 reducer checks document and kind before any insert. The PK is the backstop against concurrent creation.

- **Concurrent conflicting kinds.** Two cuts of the same document each insert the same *new* id, one as `action` and one as `dialogue`, accepted concurrently. Over 15 rounds, exactly one succeeded each time, and exactly one registry row remained with a consistent kind.
- **Kind change on an existing id** is refused as `INVALID_DRAFT` (suite).
- **Same id re-inserted in another cut** of the same document keeps the original kind (differential run).
- **After restore,** registry rows are never deleted. The restored content must match the registry (`validateScopeContent`).
- **The current read** re-verifies that the registry document and kind match for every element in the scope, and fails loudly if not.
- **Project scope.** Ids are unique *per project*, not globally, as M2 intended. The probes put different projects in one schema with identical document and element ids. Every per-project invariant and export stayed isolated.
- **Cut isolation.** A sibling cut is byte-identical apart from `projectRevision` after an acceptance in its sibling. Current state is keyed `(project, document, version)`. The 7f28dc8 scoped read uses exactly that key plus a registry lookup restricted by project and id list. There is no cross-scope read path.
- **Deliberate removal vs absence.** Removed elements are stored as `{status: removed}` tombstones in scope content and resolve to `removed`. Elements never present resolve to `unknown`. Both are preserved through PG.

## 10. Storage/performance shape

**M2's fix for whole-project snapshots survives in PostgreSQL.** Storage per revision is one semantic ChangeSet plus one full copy of each *touched* scope. It never grows with project size × revisions.

The probe used 1 screenplay × 3 cuts × 2,000 elements (6,000 scoped element states, \~110 characters each), then made 120 single-line edits through Draft → Proposal → Accept on one cut:

| Measure | Value |
| --- | --- |
| ChangeSet per revision | \~1.5 KB |
| ProjectRevision per revision | \~0.3 KB |
| Checkpoints per revision | 1 (touched scope only) |
| Checkpoint size | 427 KB raw JSON; 26 KB stored after TOAST compression (synthetic text compresses well; real prose will not) |
| Checkpoints table after 120 revisions | 3.4 MB |
| Drafts table after 120 Drafts | 2.5 MB (each holds a full element list) |
| Scopes table after 120 updates | 1.1 MB (dead TOAST versions awaiting vacuum) |
| Accept, end to end | 0.68 s at rev 1, then a flat \~1.05 s from rev 21 to rev 120 (no growth with history) |
| Draft + Proposal | \~0.8 s |
| Current scoped view | 30 ms |
| `getProjectHead` / `getRevision(5)` / `getRevision(60)` | \~290 ms each (mostly M2 validation) |
| `listHistory` | 12 ms |
| `exportAcceptedHistory` | 45 s (full replay; C5) |

Realistic Studio scale is one feature screenplay of \~1,500–2,500 elements and 2–3 cuts. Assume 150–400 KB of stored checkpoint per edit on real text. Then 1,000 accepted edits cost roughly 150–400 MB. That is comfortable for PostgreSQL and tied to editing activity, not to project size. There are no hidden large JSON duplicates beyond two:

- Restore ChangeSets embed the target scope content, and the checkpoint holds it again. Restores are rare.
- Drafts each hold a full element array.

At 3 documents × 3 cuts × 2,000 elements (18,000 scoped states), latency rises: accept takes 2.8–4.7 s and a historical read 1.35 s. The cause is M2's O(n²) validation (C2), not the SQL shape. The same sizes in memory take 2.5 s.

## 11. Story → Version → Outline → Screenplay seam

**Future Story, Outline and lineage work stays additive. The schema does not make screenplay a structural root in its generic tables.** One adapter assumption has to change first: the frozen structure described in D1.

| Question | Finding |
| --- | --- |
| Can document identity/kind carry future authored types? | Yes. `authoring_documents.kind` is free-form, checked only as lowercase-kebab, and stored as 'screenplay'. Nothing reads it yet, so Outline or Story can be added without DDL. |
| Is version/cut identity project-wide enough to group related artifacts? | Yes. `authoring_versions` is keyed by project, not by document. Feature and Festival can group a future Outline and Screenplay under the same cut id. |
| Can scoped document versions serve as lineage pins? | Yes. `(project, document, version, document_version)` plus the checkpoint at any revision is a stable, addressable pin. A pin table referencing it is purely additive. |
| Is screenplay semantics hardcoded into generic tables? | Bounded. Only `authoring_elements.kind` (a CHECK over 4 screenplay kinds) and the jsonb shape of `authoring_scopes.content` and checkpoints are screenplay-specific. Outline elements can get their own registry, or a kind-discriminated content, via new migrations. |
| Can the Proposal/history architecture target Story or Outline scopes later? | Yes. Proposals, ChangeSets and revisions are scope-keyed and operation-versioned. New operation types need an M2-style reducer version, not a schema replacement. |
| **What must change first** | `readState` builds `documents`, `versions` and the scope list from `initial_revision` JSON. A new cut or document created after revision 0 would be invisible to validation and history. Fix: enumerate structure from `authoring_documents`, `authoring_versions` and `authoring_scopes`, and add `created_in_revision` to them for historical reads. That is an additive migration plus an adapter change, done when the first structure-creating operation lands. |

Nothing in M2.5 has to be replaced to reach the target hierarchy.

## 12. Studio/server boundary

**Acceptance authority comes from the server, and database details stay out of the browser.** The only real gaps are availability and observability (B2, C3).

- **Trusted principal.** `serverAuthoringContext` is a server-side constant. The route calls `app.handle(args[0], serverAuthoringContext)` and never reads `args[1]`. The browser client's `studioAuthoringContext` export is inert and is kept only for the call surface. Verified live (§8).
- **Browser payload.** `method` is allowlisted and `args` are passed through untyped. All values reach SQL only as bind parameters. Malformed ids or scopes (`{"x":1}`, arrays, strings for numbers) return `null`, not 500.
- **Credentials.** `DATABASE_URL` is read only in `$lib/server/authoring.ts` and the migration CLI. `@light-delay/v2-core/postgres` is a separate export, imported dynamically only in PG mode. Importing `v2-core` opens no connection. No secret is committed (grep of the full M2.5 diff; the only URLs are CI's password-less trust URLs). The only connection data ever printed is pg's own dump of the client object on the B2 crash (host, port, user, database; the password is non-enumerable and was not printed).
- **v2-core independence.** Core has no SvelteKit or server import. The PG adapter implements the unchanged async M2 ports, plus `getCurrentScreenplayView`, `listDrafts` and `listProposals`, which were added to both adapters.
- **UI.** The UI still goes through the application boundary via a JSON RPC. Filmmaking UX sees statuses and messages, never SQL. The one leak is B2/C3: every server error becomes "Studio authoring is temporarily unavailable".
- **No authentication.** This is deferred as agreed, and it does *not* mean trusting browser authority. Every writer is the constant `user:local-filmmaker`. That is honest for a single-user fixture, and the docs forbid real authoring before an access boundary.
