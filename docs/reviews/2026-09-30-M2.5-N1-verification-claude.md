## 3. The correction

`apps/studio/src/lib/authoring-retry.ts:219-231`. When the command key is ambiguous (an earlier attempt failed transiently) and the resend returns `ok: false`, the helper calls `reconcile(command)` once more. It replaces the result only if that returns `ok: true`. This runs after the existing `STORE_BUSY` handling.

The reconciliation code is unchanged and uses only read requests. It returns `ok: true` only from authoritative evidence of the intended operation:

| Command | Success evidence | Otherwise |
| --- | --- | --- |
| Accept | Proposal `accepted`, with its `changeSetId` present in history and the resulting revision readable | Rejected Proposal → `ok: false` |
| Reject | Proposal `rejected` | Accepted Proposal → `ok: false` |
| Restore | A `scoped-restore` ChangeSet with the same scope and target revision, and a `DocumentVersionEquals` precondition equal to the command's expected version | Nothing found → `undefined` |
| CreateProposal | The exact Proposal ID from the same Draft | — |
| SaveDraft | A Draft with the same ID and identical elements | — |

A version advanced by another writer therefore cannot satisfy the restore check: the ChangeSet must be a scoped restore to the same target from the same expected version, and only one ChangeSet can hold that precondition. The rule is *confirmed intended outcome ⇒ success*, not *semantic failure after retry ⇒ success*.

If the final reconciliation read itself fails transiently, the loop continues within its existing budget and reconciles before any further resend.

## 4. N1 positive reproduction

**Method.** This used the probe setup of the previous review: built Studio in PostgreSQL mode with its production 20 s `query_timeout`, the real HTTP route, and Studio's retry helper. A byte-level proxy between Studio and PostgreSQL 16 held only the write transaction's `COMMIT` for 25 s, inside PostgreSQL's 30 s idle-in-transaction bound. The same run was repeated with the pre-N1 helper from `1596157`.

| Command | Request sequence (both helpers) | Pre-N1 result | Corrected result | PostgreSQL |
| --- | --- | --- | --- | --- |
| Accept | handle 503 `STORE_UNAVAILABLE` → getProposal `pending` → handle `PROPOSAL_ALREADY_RESOLVED` | failure | getProposal `accepted` → listHistory → getRevision → `proposal-accepted` | head 1, 1 ChangeSet, 1 checkpoint |
| Reject | 503 → `pending` → `PROPOSAL_ALREADY_RESOLVED` | failure | getProposal `rejected` → `proposal-rejected` | rejected, head 0, no history |
| Restore | 503 → listHistory (no restore) → `CONFLICT` "Document version changed from 1 to 2" | failure | listHistory → getRevision → `screenplay-restored` | head 2, 1 restore |

This matches all eight required steps. The original COMMIT committed about 25 s after it was sent, after the client deadline and after the pre-read saw `pending`. The resend waited on its locks and returned the semantic failure, and the final reconciliation found the intended operation.

In the browser, with the same 25 s hold on Accept, the page now shows "Accepted into project history as revision 1". It no longer offers Accept, the editor holds the accepted text, and there are 2 accept requests and 1 ChangeSet. Before the correction this showed "Proposal not accepted".

## 5. N1 negative controls

**Method.** Real lock timing, with no hooks in the transport. The original write transaction's COMMIT was held for 60 s. A rival command was issued at 16 s and queued on the same locks. At 20 s Studio's deadline answered 503, and the retry helper's pre-read saw `pending`. The resend queued behind the rival. At about 31.7 s PostgreSQL's idle-in-transaction timeout ended the original session and rolled it back. The rival then won, and the resend returned a semantic failure.

| Case | Resend | Final reconcile read | Client result | PostgreSQL |
| --- | --- | --- | --- | --- |
| My accept vs rival reject | `PROPOSAL_ALREADY_RESOLVED` | getProposal `rejected` | **`PROPOSAL_ALREADY_RESOLVED`** | rejected, head 0, no ChangeSet |
| My reject vs rival accept | `PROPOSAL_ALREADY_RESOLVED` | getProposal `accepted` | **`PROPOSAL_ALREADY_RESOLVED`** | accepted once, head 1 |
| My restore → rev 0 vs rival restore → rev 1, same expected version | `CONFLICT` | listHistory (no target-0 restore) | **`CONFLICT`** | one restore, target 1 |

The repository's negative regressions cover accept vs reject, reject vs accept, and restore vs an unrelated accepted edit that only advances the document version. All three preserve the resend's failure. No case laundered a semantic failure into success.

## 8. Test validity

- **Fault proxy** (`packages/v2-core/test-support/postgres-fault-proxy.ts`).
  - It parses frontend messages and holds only a `COMMIT` on a connection that has sent `INSERT`/`UPDATE`/`DELETE`, so read-transaction COMMITs are not held.
  - It keeps the backend open when pg discards its client, and delivers the COMMIT on `release()` or destroys both sides on `abort()`.
  - Real `COMMIT` bytes reach real PostgreSQL.
- **Deadline and responses.** The deadline is pg's real `query_timeout`, shortened to 500 ms (core) and 1500 ms (browser). `STORE_UNAVAILABLE` is not faked: the core transport maps only errors that pass `isPostgresUnavailable`, and the browser test goes through the built server.
- **Ordering.** The positive tests release the COMMIT only after `pg_blocking_pids` shows the resend blocked, which proves the COMMIT landed after the client deadline and after the pre-read. They assert the first mutation was 503 and the resend was `PROPOSAL_ALREADY_RESOLVED`/`CONFLICT`.
- **Against the pre-N1 helper** (a local, uncommitted swap): all three positive regressions fail ("expected ok: false … to match ok: true"); the negatives pass.
- **Against a laundering helper** (a local mutation that turned any post-ambiguity semantic failure into success): all three PostgreSQL negatives fail, and four unit tests fail. The tree was restored after each experiment.
- **Browser test.** It passed locally against PostgreSQL 16: Accept and Restore, 2 mutation requests each, then database assertions on head, revisions, checkpoints, projection and one restore.
- **D9 (note).** The browser test lowers the deadline through a `query_timeout` connection-string parameter. pg merges connection-string parameters *over* explicit pool options (`pg/lib/connection-parameters.js:57-60`). The same applies in production: a `DATABASE_URL` carrying `query_timeout` or `statement_timeout` would silently replace the pool bounds. This is configuration hygiene, not a defect in the correction.
