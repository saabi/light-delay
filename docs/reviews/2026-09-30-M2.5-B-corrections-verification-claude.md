## 3. Method

- Disposable PostgreSQL 16.13 and Node 22 (the owner uses 14.24; CI uses Node 24). Built Studio (`adapter-node`, `STUDIO_AUTHORING_STORE=postgres`) connected through a byte-level PostgreSQL fault proxy. The proxy parses frontend messages and can hold one connection's bytes and deliver them late in order, drop replies, cut before or after a statement, freeze every connection, or cut and refuse after a given acknowledgement.
- API probes used Studio's unmodified `authoring-retry.ts` against the real HTTP server. Browser probes drove the real page in Chromium against PostgreSQL mode.
- An integrity checker queried PostgreSQL directly after every destructive probe. It checked accepted Proposals against ChangeSets, head against revisions, revisions against ChangeSets and checkpoints, current projection against latest checkpoint, and duplicate acceptance or restore history.
- Probe scripts lived outside the repository and are not committed. This document is the artifact.

## 4. Findings

### N1. B — A timed-out COMMIT commits later; the concurrent resend reports failure for Studio's own success

*Demonstrated for accept, reject and restore through the API, and for accept in the browser.*

- **Code.** `packages/v2-core/src/postgres-authoring-store.ts:78` (`query_timeout: 20_000`) and `apps/studio/src/lib/authoring-retry.ts:178-221`. The retry loop reconciles an ambiguous command only *before* resending (`:178`). A semantic result from the resend is returned at `:219-221` without reconciling again.
- **Mechanism.** pg 8.23's `query_timeout` only rejects the JavaScript promise (`pg/lib/client.js:706-731`): no `CancelRequest`. `inTransaction` classifies `Query read timeout` as unavailable and releases the client with an error; `Client.end()` then destroys the socket. PostgreSQL keeps the transaction and its locks until it next reads the socket. If the COMMIT has already been sent, it can still commit (§8). Studio has meanwhile answered 503. The retry module reconciles, sees `pending`, and resends. The resend waits on the original's row locks. When the original commits, the resend reads the terminal state and returns `PROPOSAL_ALREADY_RESOLVED` or, for restore, `CONFLICT`.
- **Reproduction.** Proxy holds the write transaction's COMMIT for 25 s.

  | Command | Requests (API) | Client result | PostgreSQL |
  | --- | --- | --- | --- |
  | Accept | handle 503 (20.6 s) → getProposal (pending) → handle | `PROPOSAL_ALREADY_RESOLVED` | accepted once, 1 ChangeSet |
  | Reject | same | `PROPOSAL_ALREADY_RESOLVED` | rejected once |
  | Restore | handle 503 → listHistory (none) → handle | `CONFLICT` "Document version changed from 1 to 2" | 1 scoped restore |

  In the browser the page shows "Proposal not accepted: Proposal is already resolved", still offers Accept, and keeps the pre-accept editor; a reload shows the accepted state.
- **Trigger.** The COMMIT alone must stall at least 20 s while other connections work. Two plausible causes: TCP retransmission backoff on one connection after a network blip, since a fresh pooled connection works at once; or a WAL fsync stall, where reads still work. Before the B4 correction the same event produced a slow success.
- **Why B.** Sep 26 client policy item 4: after a retried attempt, `PROPOSAL_ALREADY_RESOLVED` or restore `CONFLICT` "may mean an earlier attempt succeeded. The client re-reads … and reports the actual outcome." F1 had the same user-visible effect and was classified B.
- **Integrity.** Held in every run. Row locks and terminal/scoped preconditions serialize the resend behind the original; no duplicate history.
- **Smallest correction.** In `createRetriedRequest`, when the key was ambiguous and the resend returns `ok: false`, call `reconcile(command)` once more and return its result when found. On a scratch copy of the module (not committed), all three cases then returned `proposal-accepted`, `proposal-rejected` and `screenplay-restored`, with the same single persisted mutation. Add a unit test in which the first attempt is transient and the resend returns `PROPOSAL_ALREADY_RESOLVED` while `getProposal` then reports `accepted`. Also document in `V2_POSTGRES_PERSISTENCE.md` that the 20 s deadline leaves write outcomes ambiguous rather than cancelled.

### N2. C — CreateProposal identity replay ignores `expectedDraftUpdatedAt`

`packages/v2-core/src/authoring.ts:331-341` returns an existing Proposal for the ID after checking only Draft ID and principal. Resending a *committed* ID with a newer Draft time returns the older Proposal (content FIRST for a Draft now SECOND) as `proposal-created`. The behavior is identical on both stores. The documentation claims only the uncommitted case ("an uncommitted retry"), which holds: a new ID with a stale time returns `CONFLICT`.

Studio cannot reach this in one tab. Edits reset `proposalAttemptId` and the Draft changes only through edits. It needs another tab to change the Draft after an exhausted ambiguous create, then a version switch and Review changes. Correction: record the observed Draft update time on the Proposal, or reject when `prior.createdAt` precedes `expectedDraftUpdatedAt`.

### N3. C — Pre-existing M2 Write behavior: a stale pending Proposal is offered as current

Demonstrated fault-free in one tab, with no persistence failure involved. Review changes (FIRST) → edit and Save Draft (SECOND) → reload. The page shows "Proposal ready for review" with After = FIRST beside a SECOND editor. Accept commits FIRST. The SECOND Draft is then treated as consumed and disappears from the UI; it remains in PostgreSQL.

- **Code.** `apps/studio/src/routes/+page.svelte:94-112` (`openVersion`), from `8835971` (M2, before the M2.5 baseline). It behaves the same in memory mode.
- **Why C.** The review panel does show the content being accepted, and nothing durable is lost. This is Write UX, not persistence; it belongs to the next Studio milestone.
- **Correction.** Surface only pending Proposals created after the Draft's last update, or mark older ones superseded.

### D notes

- **D5 — timeout composition.** statement 15 s < client query 20 s < idle-in-transaction 30 s. PostgreSQL cancels normal slow statements and lock waits first, cleanly. The 20 s deadline fires only when the server or network stops responding, and it cancels nothing. Mid-transaction work aborts once PostgreSQL reads EOF. A COMMIT delivered within PostgreSQL's 30 s idle bound can commit (§8). The composition is safe for integrity; its ambiguity is what N1 must reconcile. `client_connection_check_interval` (PostgreSQL 14+) is unset, but statement_timeout already bounds long statements.
- **D6 — keepalive.** Confirmed armed on Studio's sockets at about 10 s (`/proc/net/tcp` timer `02:000003E3`). Probe interval and count stay at the OS defaults of 75 s × 9. pg-pool's default 10 s idle timeout closes idle clients first. The effective bounds are the 5 s connect timeout and the 20 s query deadline; keepalive is harmless but adds little.
- **D7 — autocommit writes after the deadline.** `createProposal` and `saveDraft` are single autocommit statements, so a delayed one commits whenever it arrives. CreateProposal is safe through the primary key. `saveDraft` has no monotonic guard, so a very late SaveDraft could overwrite a newer Draft; B2's `expectedDraftUpdatedAt` then turns the next Review into `CONFLICT`. This was analysed but not demonstrated.
- **D8 — Proposal ID namespace.** Caller-supplied Proposal IDs must match the generic ID pattern only; `draft:not-a-proposal` is accepted as a Proposal ID on both stores. This has no security consequence for one principal. Consider requiring the `proposal:` prefix.
- **D1 (carried).** The editor stays disabled for the whole bounded wait (26–42 s observed).

## 5. B1 — committed mutation vs failed refresh

State machine (`+page.svelte`): `refreshCommitted` and the CreateProposal `refresh` set `activeAction` and `retryAction` to the refresh closure. The connection listener captures the refresh, not the mutation. `perform` clears `retryAction` only when it equals the action. Reject has no post-commit refresh.

| Probe (Studio in PostgreSQL mode, Chromium) | Mutation requests | Result |
| --- | --- | --- |
| Accept; proxy cuts every connection and refuses new ones right after the accept COMMIT acknowledgement | 1 | "…revision 1 · Authoritative refresh pending", banner; after recovery Retry now → "Accepted … revision 1", history 1 ChangeSet, editor accepted text |
| Restore to Initial after an accepted edit; same outage after the restore COMMIT | 1 | Retry now → "Restored as new project revision 2", editor original text (not stale), 1 restore |
| Only the view read fails (4×) | 1 | Banner; Retry now refreshes |
| Only the history read fails (4×) | 1 | Banner; Retry now refreshes |
| Both reads fail twice, then succeed | 1 | No banner; accepted state shown |
| View fails 4×, history recovers on its 4th attempt | 1 | Banner; Retry now refreshes |
| CreateProposal committed; base-revision read fails | 1 CreateProposal | "Review refresh pending"; Retry now shows the Proposal; 1 row |

The acceptance property holds: a failure to read a committed result never turned Retry now into a resend. N1 is a different path. There the outcome was genuinely unknown and the resend was automatic.

## 6. B2 — Proposal identity

Mechanism: an optional caller ID and observed Draft time are enforced in `AuthoringApplication`, shared by both stores. It reads the prior Proposal for the ID and returns it when Draft and principal match, otherwise `CONFLICT`. It checks the Draft time for new creations. The insert uses `ON CONFLICT (project_id, proposal_id) DO NOTHING` on the persisted primary key and re-reads on conflict. Reconciliation reads the exact ID. The mechanism is narrowly scoped to CreateProposal; no generalized command-ID system was introduced.

## 8. B4 — bounded progress and server work after the deadline

**Waiting is bounded.** With the database frozen but connected: raw read or accept → 503 in 20.5 s on a warm connection and 5.0 s on a new one. The retry client reaches `unavailable` in 26.5 s (cold) or 42.4 s (warm). In the browser, Save Draft disabled the editor, showed "Reconnecting… (attempt n of 3)", and reached the banner at 26.4 s. Typed text was kept, and after recovery Retry now saved it. Accept retries ended `unavailable`; a later Retry now reconciled (pending) and accepted once.

**What the deadline does: C then B.** It stops the JavaScript wait only (`pg/lib/client.js:706-731`, no cancel). The store then discards the client, and `Client.end()` destroys the socket because a query is still active. PostgreSQL work continues until the backend next uses the socket.

| Stalled message (single request, no retries) | HTTP | Server afterwards |
| --- | --- | --- |
| `UPDATE authoring_projects …` mid-transaction, delivered at 25 s | 503 at 20.5 s | Transaction "idle in transaction" holding locks until 25 s, then aborted on EOF; nothing committed |
| COMMIT delivered at 25 s | 503 at 20.6 s | **Committed at ~25 s**: accepted, head 1, 1 ChangeSet, integrity clean |
| COMMIT delivered at 36 s | 503 at 20.6 s | Session ended at 30 s by idle-in-transaction timeout; nothing committed |

Answers to the §8 questions:

- **Can a timed-out transaction commit?** Yes, but only if its COMMIT was already sent: between 20 s and the 30 s idle bound for a network stall, or unbounded if PostgreSQL stalls while processing the COMMIT.
- **Is the connection discarded?** Yes, Studio's side always.
- **Is cancellation acknowledged?** None is sent.
- **Does rollback always occur?** Only for work without a sent COMMIT.
- **Does reconciliation resolve the ambiguity?** Only once the original has finished. A later retry cannot race the original into a duplicate, because it serializes on the same row locks.
- **Duplicate history?** Never.
- **Can the UI report failure for a success?** Yes — N1.

## 10. Store parity, client policy, no queue

- **Parity.** `authoring.test.ts` is byte-identical to `1fd9024`. Locally: in-memory 83/83 (36 contract), PostgreSQL 68/68 (36 contract + 2 new). No test schemas were left behind.
- **Client policy** (unmodified module, fake transport).
  - Network failure, 503 `STORE_UNAVAILABLE` and command `STORE_BUSY` each make 4 requests, with sleeps within 375–625 / 1125–1875 / 3000–5000 ms.
  - `Retry-After` 10 s is honored; 3600 s is capped at 60 s; an HTTP-date is honored; garbage is ignored.
  - `CONFLICT`, `INVALID_COMMAND`, `PROPOSAL_ALREADY_RESOLVED`, `REVISION_NOT_FOUND`, `NO_CHANGES`, 500 and 400 are sent once. Gateway 502/503/504 without a code are sent once (F6).
  - Reconciliation uses the single-shot path, and the server never replays. Retry multiplication is limited to parallel reads each carrying their own bounded retries.
- **No queue.** Studio and v2-core contain no mutation queue, browser storage, service worker, timer or Redis; no such dependency exists. The only server loop is the bounded stale-head retry. PostgreSQL remains the sole durable authority.
